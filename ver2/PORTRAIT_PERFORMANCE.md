# 박지민 표정 전환 최적화

작업일: 2026-11-13. 실행 진입점: `../index_ver2.html`.

## 범위

사용자의 이번 지시에 따라 루트 `index.html`은 수정하지 않았다. 현재 저장소에는 이전 파일명 변경으로 `index_ver2.html`이 없었으므로 현행 V2 HTML을 복사해 해당 진입점을 다시 만들고 자체 시작 링크와 첫 이미지 preload를 지정했다.

두 HTML이 `ver2/`의 JS·CSS를 공유하므로 **공유 코드의 최적화는 기존 배포 진입점에서도 동작한다.** `index.html`의 파일 내용·이름은 유지한다. 변경 전후 SHA-256은 `0814BF287EF9A933321704ACD9AC2B893BA432AEE1C948A840915E8BBD965871`이다.

## 확인한 원인과 미확인 사항

| 항목 | 확인 결과 |
| --- | --- |
| 표정 사전 로딩 | 기존 구현에 `Image()` preload·`decode()`·decoded Image 캐시가 없었다. |
| DOM 재생성 | 이전·다음 및 엔딩 대화마다 `main.innerHTML = UI.scene(...)`으로 캐릭터를 포함한 전체 장면을 재생성했다. |
| CSS 지연 | 수초의 `animation-delay`는 없었다. 화자 강조는 250ms, 진술 패널 등장은 220ms였으므로 긴 네트워크·디코딩 대기를 설명하지 못한다. |
| PNG 해상도 | 339~357 × 443~453px. 모바일 표시를 위해 해상도를 더 줄일 이유는 없다. |
| PNG 용량 | 개별 240,872~262,785 bytes, 8종 합계 2,011,879 bytes. |
| 경로 | 표정 이름·대소문자·확장자 및 파일 존재를 확인했다. 원본 경로와 WebP 경로를 별도로 관리한다. |
| 반복 다운로드 | DOM 재생성만으로 매번 실제 다운로드가 발생한다고 단정할 수는 없다. 기존 코드에 cache-busting 쿼리는 없었다. 첫 사용의 미준비 상태와 이미지 객체 재생성은 확인했다. |
| Cloudflare 캐시 헤더 | 기존 배포 `https://find-game.pages.dev/ver2/assets/case02/characters/ParkJimin_01_neutral.png`에 읽기 전용 HEAD 요청을 수행했다. 200, `image/png`, `Cache-Control: public, max-age=0, must-revalidate`, `ETag: "00524d5035747c115c5786b3bb14cce0"`를 확인했다. ETag 재검증이 가능한 응답이며, 실제 브라우저에서 재검증·전송이 몇 번 발생하는지는 Network trace가 필요하다. |
| 실제 브라우저 캐시 | 실제 Network trace는 확보하지 못했다. 기존 응답은 재검증 정책이지만 그것만으로 표정 전환마다 전체 PNG가 전송된다고 단정할 수 없다. 캐시 설정을 임의로 바꾸지 않았다. |

긴 지연의 주원인 후보는 **첫 사용 시 다운로드·디코딩 대기와 장면/이미지 DOM의 반복 교체**다. 실제 배포 환경에서의 비중은 네트워크 측정이 필요하다.

## 변경 방식

1. `UI.portraits`에서 8개의 실제 `Image` 객체를 유지한다. 중복 preload는 동일한 Promise를 재사용한다.
2. 첫 기본 표정을 높은 fetch priority로 먼저 로드·디코딩하고, 나머지 표정을 병렬 준비한다. 시작 개요 타이핑 중 작업한다.
3. `load` 이후 `decode()`까지 완료해야 ready로 기록한다. decode 미지원 브라우저는 `load`를 사용한다.
4. 시작 버튼은 개요 표시 완료 및 전체 로딩 시도 완료 후 활성화한다. 준비 수를 표시하고 전부 실패하면 시작을 막고 재시도 버튼을 제공한다. 일부 실패 시 준비된 표정으로 진행할 수 있다.
5. 시작 시 이미 디코딩한 8개의 이미지 객체를 장면의 `.portrait`에 붙인다. 같은 장면에서 이전·다음 클릭은 장면·캐릭터·명패 DOM을 교체하지 않는다. 진술 내용과 조작 버튼만 갱신한다.
6. 표정은 `opacity`만 즉시 변경하고 180ms 동안 크로스페이드한다. 기존 프레임을 제거하거나 src를 다시 지정하지 않는다. 화자 축소·확대 250ms는 기존 디자인대로 유지한다.
7. 클릭 경로에는 이미지 다운로드·디코딩·완료 타이머를 두지 않는다. 방어적으로 미준비 이미지 완료를 기다릴 경우에도 sequence 번호가 최신인 경우만 반영한다.
8. WebP 실패 시 원본 PNG를 시도한다. 양쪽이 실패하면 기존 보이는 표정을 유지하고 `console.warn('[FIND portrait]', detail)` 및 `UI.portraits.errors`에 경로·오류·시각을 기록한다. 단일 포맷당 로딩·디코딩 상한은 12초이며 시작 화면에서 재시도할 수 있다.
9. OS 동작 줄이기 또는 화면의 효과 줄이기에서는 크로스페이드 없이 즉시 전환한다.

## 에셋 비교

원본 PNG는 모두 보존한다. WebP는 같은 해상도의 **무손실** 파일로 `assets/case02/characters/optimized/`에 별도 저장한다. 모든 알파값 일치와 밝은/어두운 배경 합성 픽셀 일치를 검사했다.

## 검증 결과와 한계

- `node ver2/test-portraits.cjs`: 다운로드·decode 순서를 제어하는 Image/DOM 모형으로 우선순위, 디코딩 전 시작 방지, 중복 요청 방지, 128회 순방향·역방향·빠른 전환, 장면/캐릭터 DOM 유지, 탭 복귀 객체 재사용, 역순 완료 방어, WebP 실패→PNG, 양쪽 실패 시 기존 표정 유지·로그, 재시도 및 timeout을 검사한다.
- `node ver2/test-flow.cjs`: 준비 진행·모두 실패 시 시작 차단, 기존 세 판정의 도입→증거→검증→엔딩→재플레이, 정보 기록·해제, 판정 검토, 화면 설정, 에셋 경로 및 색상 대비 회귀 검사를 수행한다. 이 테스트는 이미지 전송을 모의하고, 실제 로더는 별도 테스트에서 검사한다.
- Pillow 검사: 무손실 WebP 8종의 해상도, 알파 및 밝은/어두운 배경 합성 픽셀 일치를 검사한다.
- JS 문법 검사와 `index.html` 해시 보존 확인.
- 기존 Cloudflare 배포의 PNG HEAD 응답 확인: 200·PNG Content-Type·재검증 Cache-Control·ETag. 수정본은 배포하지 않았다.
- 브라우저 검증 시도: 기존 배포 창의 접근성 정보는 확인했으나 로컬 파일 진입을 위한 입력 단계에서 `coordinate input geometry is unavailable` 오류가 발생해 로컬 시각 검증은 완료하지 못했다.
- **미검증:** 실제 브라우저의 첫 프레임 시간, 모바일 GPU에서의 크로스페이드·깜빡임, 실제 HTTP 캐시 재사용, 수정본의 Cloudflare Pages 실배포. 모형 테스트의 즉시 상태 전환을 실제 브라우저 지연 측정으로 표현하지 않는다.

### 배포 후 확인 절차

1. Cloudflare 배포에 `index_ver2.html`, 변경 JS/CSS, `optimized/*.webp`가 함께 포함되는지 확인한다. 루트 변경과 임의 `_headers`는 필요하지 않다.
2. 캐시를 비운 첫 접속에서 Network 탭의 8종 요청과 시작 화면 준비 완료를 확인한다. WebP 200/304 또는 브라우저 캐시 결과, Content-Type, Cache-Control, ETag를 기록한다.
3. 다음·이전·연속 클릭 후 이미지 요청이 늘어나지 않고 대사와 표정이 일치하는지 확인한다. Disable cache 상태에서도 대화 중 src 재지정 요청이 없는지 확인한다.
4. 모바일에서 180ms 전환의 깜빡임 및 효과 줄이기 즉시 전환을 육안 확인한다.
5. 특정 WebP만 차단해 PNG 대체를 확인하고, 두 포맷을 모두 차단해 현재 이미지 유지와 console 오류를 확인한다.
